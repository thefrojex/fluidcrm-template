# FluidCRM relational data model

This is the **logical data model** for FluidCRM: tables, columns, relationships, enums and the business rules that sit on top of them. It's deliberately stack-agnostic. An agent building the backend should pick its own database, ORM and API framework and translate the types below.

The app is managed by **both humans and AI agents**. That one fact shapes most of the design: every row records who (or what) created and changed it, AI output is stored as reviewable proposals with provenance, writes are versioned and idempotent, and nothing an agent does is destructive or irreversible.

Related docs:
- [UI-DECISIONS.md](UI-DECISIONS.md): what the page shows and why. Its rules are the source of truth for derived values.
- [AI-AGENTS.md](AI-AGENTS.md): the deal-context JSON given to agents, the suggestion pipeline, permissions and tool definitions.

## 1. Conventions

| Topic | Convention |
| --- | --- |
| Primary keys | `id uuid`, generated by the server. UUIDv7 recommended (time-ordered, good for indexes and for agents reading logs in order). |
| Tenancy | Every business table has `workspace_id`. Every query is scoped by it. |
| Timestamps | `timestamptz`, stored in UTC. `created_at`, `updated_at` on every mutable table. |
| Calendar dates | `date` (no time) for event days. "Today" and "overdue" are evaluated in the **workspace's timezone** (`workspaces.timezone`), never UTC. |
| Actors | Every write stores an `actor_id` referencing `actors` (section 3), which can be a human, an AI agent, an automation or the system. Columns are `created_by`, `updated_by`, and action-specific ones like `completed_by`. |
| Soft delete | Business rows have `deleted_at timestamptz null` and `deleted_by`. Nothing is hard-deleted through the app or the agent tools. This is what makes Undo and AI auditability possible. Every list query filters `deleted_at is null`. |
| Optimistic concurrency | Mutable rows have `version integer not null default 1`, incremented on every update. Writers send the version they read; a mismatch is a conflict (`409`) and the writer must re-read. Humans and agents editing the same deal at once is expected. |
| Money | `numeric(14,2)` amount + `char(3)` ISO currency + a period enum. Never strings like `'₹45L/yr'`. |
| Enums | Listed in section 2. Store as text with a check constraint, or as native enums. Values are lowercase snake_case. |
| JSON | `jsonb` (or the DB's JSON type) only for snapshots, payloads and diffs, never for data that's queried or joined. |

## 3. Entity overview

```
workspaces ─┬─< workspace_members >── users
            ├─< agents
            ├─< actors  (one per user / agent / automation / system)
            ├─< companies ─< contacts
            │       └─< deals ─┬─< deal_events ─┬─< reminders ─< reminder_deliveries
            │                  │                └── ai_suggestions (0..1, provenance)
            │                  ├─< ai_suggestions
            │                  └─< ai_runs
            ├─< activity_log  (every write, by any actor)
            └─< idempotency_keys
```

`>─<` means many-to-many through the join table; `─<` means one-to-many.

- `origin = 'ai'` ⇔ `ai_suggestion_id is not null`
- `ai_review_status = 'pending'` ⇒ `completed_at is null` (you can't complete an unaccepted suggestion)
- the owner columns match `owner_kind`

**Why pending suggestions live in `deal_events`:** the UI renders a suggestion as a normal card in its date position, editable with the same form. Storing it as a real event row with `ai_review_status = 'pending'` means one table, one editor and one set of APIs. Accepting is a single status flip, not a copy. Every metric query must exclude `pending` (section 6.3).

## 5. Relationships and delete behaviour

| Parent → child | Cardinality | On parent soft-delete |
| --- | --- | --- |
| workspace → everything | 1 → many | n/a (workspaces are archived, not deleted) |
| company → contacts | 1 → many | Soft-delete the contacts too. |
| company → deals | 1 → many | Soft-delete the deals (and through them, their events). |
| deal → deal_events | 1 → many | Soft-delete the events, with the same `deleted_at`, so a restore can bring back exactly that set. |
| deal_event → reminders | 1 → many | Set scheduled and draft reminders to `cancelled`. |
| deal_event ↔ ai_suggestion | 1 ↔ 0..1 | Dismissing a suggestion soft-deletes its event. Deleting an AI event whose suggestion is still pending sets the suggestion to `dismissed`. |
| deal → ai_runs | 1 → many | Keep (audit). |

Restoring a parent restores children that share its exact `deleted_at`, and re-schedules reminders whose `remind_at` is still in the future.

## 6. Business rules

These rules must be identical everywhere: API, UI and agents. The current implementation of the derived ones is in `src/lib/deals.js`.

### 6.1 Ordering
- A deal's timeline is ordered by `event_date`, then `sort_key`.
- **Insert between two events** (the hover **+** in the UI): the new event gets the left neighbour's `event_date`, and a `sort_key` between the neighbours' keys (fractional indexing). Insert at the end: the last event's date and a larger key.
- Changing `event_date` moves the card; keep its `sort_key` unless it collides.

### 6.2 AI suggestions: "AI proposes, humans dispose"
- **Creation:** an agent creates an `ai_suggestions` row and a `deal_events` row with `origin = 'ai'` and `ai_review_status = 'pending'`, in one transaction. Reminders proposed with it are created with `status = 'draft'`.
- **Draft reminders never fire.** They're scheduled only when the suggestion is accepted.
- **Accept** (human only): suggestion `status = 'accepted'`, `reviewed_by`, `reviewed_at`, and `edited_fields` computed from the diff; event `ai_review_status = 'accepted'`; draft reminders become `scheduled` (or `cancelled` if their time has already passed). `origin` stays `ai`, so the card keeps its AI tag.
- **Dismiss** (human only): suggestion `status = 'dismissed'` plus an optional `dismiss_reason`; the event is soft-deleted; its reminders are `cancelled`.
- **An agent must never accept or dismiss**, including its own suggestions. It can edit or withdraw (`superseded`) its own pending suggestions, for example when a newer run replaces them.
- **Expiry:** a daily job sets pending suggestions whose `event_date` is before today to `expired` and soft-deletes their events. A suggestion for a day that already passed is noise.
- **Limits:** at most `settings.max_pending_suggestions_per_deal` (default 3) pending per deal. An agent must not create a suggestion whose `dedupe_key` matches a pending one, or one dismissed in the last 30 days.
- **Human edits to a pending suggestion** are allowed and recorded in `edited_fields` on accept.

### 6.3 Status and metrics (derived; don't store)
Evaluate with `today` = the current date in `workspaces.timezone`:

| Status | Rule (checked in order) |
| --- | --- |
| `suggested` | `ai_review_status = 'pending'` |
| `done` | `completed_at is not null` |
| `overdue` | `event_date < today` |
| `next` | the first remaining event in timeline order (at most one per deal) |
| `upcoming` | all others |

- **Committed events** = all non-deleted events except `suggested`. Only committed events count toward progress (`done / total`), overdue counts, the Overdue filter, "due in next 7 days" and "next".
- **Due in next 7 days** = committed, not done, `today <= event_date <= today + 7`.
- **Pipeline value** = sum of `value_amount` over the visible open deals, converted to the workspace currency. Don't mix currencies without converting.
- **Stale deal** = open, with `last_activity_at` older than 7 days and no `next` event. This triggers a `deal_stale` AI run.

### 6.4 Completion
- Completing sets `completed_at = now()` and `completed_by`. Reopening clears both.
- When an event is completed, its still-`scheduled` reminders are `cancelled` if `settings.cancel_reminders_on_complete` is true (default true). There's nothing left to remind about.
- Completing an event triggers an `event_completed` AI run for that deal (debounced, see AI-AGENTS.md §3).

### 6.5 Reminders
- A new reminder that isn't a draft must have `remind_at` in the future and becomes `scheduled`.
- The recipient must be reachable on the channel: email needs an email address, WhatsApp and SMS need a phone number, in-app needs a user. Validate on write; don't fail later at send time.
- The scheduler picks `status = 'scheduled' and remind_at <= now()`, sets `sending`, writes a `reminder_deliveries` row, then `sent` (with `sent_at`) or `failed` (with `failure_reason`, retried with backoff up to 3 attempts).
- Editing `remind_at` or the recipient of a `sent` reminder is not allowed. Create a new one.
- **UI tag contract:** "N reminders" counts all non-deleted, non-cancelled reminders. The tag is grey when none are `scheduled`. Its tooltip shows the earliest `scheduled` one. `failed` should show in red (not built yet).

### 6.6 Validation shared by humans and agents
- `companies.name` and `deal_events.title` are non-empty after trimming.
- Value fields are all-or-nothing: amount, currency and period are all set, or all null.
- Every write includes the row's `version`. A stale version is a conflict, not an overwrite.
- Every agent write includes an idempotency key.

### 6.7 Undo
The UI offers Undo for ~4.5s after delete, complete, reopen, accept and dismiss. Implement it as **"apply the inverse of `activity_log.changes` for that `request_id`"**: restore the soft delete, clear `completed_at`, set a suggestion back to `pending`, and so on. It is not a snapshot overwrite, because other actors may have written in between.

## 9. Open questions

1. **Tag vs segment:** `deal_tag` mixes temperature (hot/warm/cold) and segment (enterprise). Splitting it into `temperature` + `segment` is cleaner, but the UI shows one chip. If split, decide the display rule (for example, show ENTERPRISE when segment is enterprise, else temperature).
2. **Multiple deals per company:** the schema supports it, the board doesn't yet (one row per company).
3. **Team ownership:** `owner_kind = 'team'` has no teams table yet. Add `teams` and `team_members` when needed.
4. **Relative reminders** ("1 hour before the event") would need `offset_minutes` and recomputing `remind_at` when the event moves.
5. **Currency conversion source** for the pipeline total when deals use different currencies.
